## Goal
- Build dynamic in-run clarification for Ora agents: an agent can call a safe internal tool during execution to ask the user a focused clarification question, provide LLM-generated selectable options, pause the run, then resume from either a selected option or free-form user input.

## Scope / Out of scope
- In scope:
  - Add option-bearing clarification schema shared by runtime and desktop.
  - Add agent-callable `user.clarify` runtime tool.
  - Convert `user.clarify` tool calls into existing `ClarificationInterruptError` / `pendingClarifications` / resume flow.
  - Desktop support for displaying selectable clarification options while preserving free-form input.
  - Runtime and desktop tests for interrupt, resume, option display, and backwards compatibility.
- Out of scope:
  - Multi-select clarification UI.
  - New external service/API.
  - Changing approval semantics or destructive tool policies.
  - Reworking unrelated chat UI architecture.

## Constraints
- Compatibility: existing intent preflight and static node `clarificationQuestion` flows must continue working with no options.
- Performance: `user.clarify` should not trigger extra model calls; options are generated by the calling agent/model in tool args.
- Risk: `user.clarify` is safe/internal and must not require approval or mutate local/external state.
- Tool/Environment limits: preserve existing run resume patch format `{ clarifications: { [key]: answer } }`.

## Plan
1. Shared schema: update `packages/shared/src/runtime.ts` to add `PendingClarificationOptionSchema` and optional/default `options` on `PendingClarificationSchema`.
2. Runtime clarification helper: update `apps/runtime/src/harness/runtime-clarifications.ts` so `ensureRuntimeClarification()` accepts and emits options.
3. Runtime tool registration: update `packages/shared/src/capabilities.ts` and `apps/runtime/src/harness/runtime-tool-executor.ts` to register/describe `user.clarify` as a safe implemented tool with JSON schema and examples.
4. Runtime tool loop: update `apps/runtime/src/harness/node-runtime-loop.ts` and `apps/runtime/src/harness/runtime-kernel.ts` so `user.clarify` is intercepted during tool execution and converted into `ensureClarification()` interrupt.
5. Desktop data/model: update `apps/desktop/src/types.ts`, `apps/desktop/src/lib/viewModel.ts`, and `apps/desktop/src/lib/useRunActions.ts` to expose options and submit selected option values via existing resume patch.
6. Desktop UI: update the chat message/input rendering component(s), likely `apps/desktop/src/components/ChatInput.tsx` or adjacent chat message components, to display option chips/buttons and keep free-form input available.
7. Tests: update `apps/runtime/test/runtime-smoke.test.ts`, `apps/runtime/test/desktop-composer-state.test.ts`, and `apps/desktop/src/lib/viewModel.test.ts`; run targeted tests and type checks.

## Decisions
- Decision: represent suggested answers as `PendingClarification.options` and keep final answer storage in existing `context.clarifications`.
  - Why: minimal data model change; preserves current resume and prompt-context pipeline.
  - Alternatives: separate answer channel or new continuation type.
  - Tradeoffs: v1 is single-answer only; multi-select can be added later.
- Decision: implement `user.clarify` as a safe internal runtime tool but intercept it in node runtime loop instead of normal executor return.
  - Why: the desired behavior is run interruption, not a tool result returned to the model.
  - Alternatives: make executor throw a custom error, or return sentinel output.
  - Tradeoffs: node loop gets one special-case branch, but interruption semantics stay explicit.
- Decision: option click submits immediately using existing resume patch.
  - Why: simplest interaction and matches the user's request for selection.
  - Alternatives: fill composer first and require submit.
  - Tradeoffs: immediate submit is faster but less editable; free-form input remains available.
