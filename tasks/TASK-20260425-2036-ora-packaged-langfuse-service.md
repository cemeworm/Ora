## Goal
- Upgrade Ora's Langfuse integration from "runtime can point at a manually supplied local service" to a packaged Mac app service contract: the Tauri build should include a managed Langfuse compose project, the desktop sidecar should start and health-check that bundled service without user-provided paths, and Trails should only deep-link when Langfuse is truly ready.

## Scope / Out of scope
- In scope:
  - Add a source-managed Langfuse compose bundle and package/stage it into `apps/desktop/src-tauri/resources/langfuse`.
  - Wire Tauri bundle resources so packaged `.app` contains both `runtime-sidecar` and `langfuse`.
  - Improve desktop sidecar service startup/readiness from port-open to Langfuse readiness endpoint.
  - Add focused tests and package artifact inspection.
- Out of scope:
  - Bundling Docker Desktop or a container runtime itself.
  - Replacing Langfuse's Docker Compose architecture with a native single binary.
  - Redesigning Trails visual layout.

## Constraints
- Compatibility: keep current Tauri v2 resource layout and existing runtime sidecar packaging flow.
- Performance: Langfuse startup should happen once at app startup and health checks should be bounded.
- Risk: Langfuse v3 compose stack needs Docker; app must report a clear unavailable state when Docker is missing.
- Tool/Environment limits: this machine may lack `rustfmt`; generated resources under `apps/desktop/src-tauri/resources/*` should stay out of git unless source-managed.

3. Strengthen Rust sidecar readiness/startup behavior and tests for bundled resource discovery.

## Decisions
- Decision: keep Langfuse as a bundled Docker Compose project rather than attempting to embed Docker or rewrite Langfuse as a native sidecar.
  - Why: official Langfuse v3 self-hosting is Docker Compose with web, worker, Postgres, ClickHouse, Redis, and MinIO; bundling Docker itself is not realistic for a normal macOS app.
  - Alternatives: require manual `ORA_MANAGED_LANGFUSE_COMPOSE_DIR`; build a native local observability store.
  - Tradeoffs: app owns the compose files and startup, but host still needs a container runtime.

### Item 1
- Pitfall: Tauri resource paths in `tauri.conf.json` must exist before Cargo build scripts run, even if `beforeBuildCommand` normally generates their contents.
- Symptom: the first focused Cargo test failed with `resource path resources/langfuse doesn't exist`.
- Root Cause: `resources/langfuse/docker-compose.yml` is generated by package staging, but Cargo tests invoke Tauri build logic without that staging step.
- Reusable Guardrail: keep a source-controlled `.keep` in generated resource directories that are referenced by Tauri config, and ignore generated payloads inside that directory.
- Evidence: `apps/desktop/src-tauri/resources/langfuse/.keep` is tracked while `docker-compose.yml` is ignored and regenerated by `pnpm --filter @ora/runtime package:sidecar`.
